src/data/store.ts

01 · State that survives Next.js splitting itself in two.

The idea. Next runs the boot hook (instrumentation.ts) in a different module instance than the request handlers. A normal module-level cache set at boot is invisible to pages — and worse, an index built once from the startup simulation would keep serving stale rows after live data swapped in. The fix: keep the snapshot on globalThis, and key every lookup index to the snapshot's identity, so any instance rebuilds the instant the active snapshot changes.

The code
// instrumentation.ts runs in a SEPARATE module instance from request handlers,
// so keying the indexes to the snapshot IDENTITY (shared on globalThis) makes
// every instance self-heal the instant the active snapshot swaps. (WC-044)
function syncIndexes() {
  const snap = dataset();
  if (_indexedSnap === snap && _teamIndex && _matchIndex) return;
  _teamIndex  = new Map(snap.teams.map((t) => [t.id, t]));
  _matchIndex = new Map(snap.matches.map((m) => [m.id, m]));
  _indexedSnap = snap;
}

export const getTeam  = (id) => teamIndex().get(id);   // syncIndexes() runs first
export const getMatch = (id) => matchIndex().get(id);
What it does

Every accessor in the app — getTeam, getPlayer, getMatch — calls syncIndexes() first. That one identity check (_indexedSnap === snap) is O(1) on the hot path and rebuilds the four Maps only when the snapshot pointer actually changes: live-load completion, a score refresh that swaps in a new snapshot, or a tournament switch. It's the fix for the nastiest class of bug in the project — "live data loaded but every page rendered empty" — where the rows were present but the lookups pointed at a stale index.

src/analytics/poisson.ts

02 · The match model: two λ's and a shared component.

The idea. Every prediction comes from a bivariate-Poisson goals model. Each side's expected goals (λ) is its attack against the opponent's defense, nudged by home advantage. The "bivariate" part is a shared component l3 that couples the two scores — because World Cup games aren't two independent coin-flips; when one side is scoring, the game tends to open up.

The code
export function expectedGoals(attack, defense, isHome) {
  const atk = attack.attackRating / 75;      // ratings are 0..100 → ~0.9..1.2
  const def = defense.defenseRating / 75;
  const homeMul = isHome ? 1.12 : 0.94;    // home-field bump
  return Math.max(0.18, LEAGUE_AVG_GOALS * atk * (2 - def) * homeMul);
}

// Bivariate Poisson: the shared component l3 ties the two scores together,
// so a 2-2 is likelier than "independent" Poisson would ever predict.
const l3 = cov * Math.min(lambdaHome, lambdaAway);
const l1 = Math.max(0.05, lambdaHome - l3);
const l2 = Math.max(0.05, lambdaAway - l3);
// P(x,y) = Σ_k  pmf(x−k, l1) · pmf(y−k, l2) · pmf(k, l3)
What it does

From those λ's it builds a 9×9 joint scoreline matrix, then reads everything off it by summation: homeWin (cells where x>y), draw, awayWin, both-teams-to-score, over-2.5, clean-sheet odds, and the six most-likely exact scores. One matrix, every market — and the same expectedGoals is reused to sample scorelines inside the simulator, so the forecast and the single-match prediction share one model.

src/analytics/simulate.ts

03 · Playing the tournament out 8,000 times.

The idea. Point predictions can't answer "what are Spain's odds to reach the final." So the simulator locks in finished results, extrapolates live matches, and plays out the entire remaining tournament thousands of times — completing groups by sampling Poisson scorelines, seeding the bracket, and resolving each knockout tie by ELO win-expectancy. Aggregating the runs gives every probability the app quotes.

The code
export const RUNS = 8000;   // stable to a few tenths of a %; a full rebuild is ~0.5s

// Single elimination: play each pair by ELO win-expectancy, tally survivors.
while (alive.length > 1) {
  const next = [];
  for (let i = 0; i < alive.length; i += 2) {
    const a = alive[i], b = alive[i + 1];
    const winner = rng.next() < eloExpectation(team(a).elo, team(b).elo, 0) ? a : b;
    next.push(winner);
  }
  alive = next;
  markSize(alive);   // +1 for every team still alive at this bracket size (r16/qf/sf/final/title)
}
What it does

Across 8,000 runs it accumulates, per team, how often they reach each round and lift the trophy, then divides by RUNS for a probability. A deterministic seeded PRNG (new Rng(424242)) makes it reproducible. Crucially the whole 0.5s rebuild fires only on a match status flip (kickoff, full-time) — routine score ticks reuse the cached engine, so live pages stay fast.

src/lib/format.ts

04 · The five lines that fix knockout football.

The idea. The model outputs win / draw / loss — correct for the group stage, wrong for the knockouts, where a draw isn't a result: it goes to extra time and penalties and someone advances. Rather than complicate the core model, one pure helper folds the draw probability into each side's chance to advance, split by their normal-time win ratio (the stronger side is likelier over ET + pens; 50/50 on a dead heat).

The code
// A knockout can't end level: fold the draw into each side's chance to
// ADVANCE, split by their normal-time win ratio. Sums to 1. (WC-058)
export const advanceProbabilities = (p) => {
  const decisive  = p.homeWin + p.awayWin;
  const homeShare = decisive > 0 ? p.homeWin / decisive : 0.5;
  return {
    home: p.homeWin + p.draw * homeShare,
    away: p.awayWin + p.draw * (1 - homeShare),
  };
};
What it does

It's display-only — the engine is never touched — but it ripples everywhere the tournament is knockout: the match cards show "% to advance" instead of a meaningless draw bar, and the Track Record grades knockout ties two-way (which side went through, penalties included) instead of scoring a shootout as a "draw." A tiny function that makes the whole app phase-aware.

src/ai/llmParse.ts

05 · The AI answers nothing. It only rephrases the question.

The idea. Natural-language questions are handled by a deterministic parser first. A language model is bolted onto the front as a strict translator: it only fires when the parser returns unknown, and it rewrites the question into a canonical query the parser does understand. The model never sees a statistic, so it can't invent one — the engine computes every number.

The code
export async function smartAnswer(rawQuery) {
  const deterministic = answerQuery(rawQuery);
  if (deterministic.intent !== 'unknown') return deterministic;   // already handled

  const normalized = await llmNormalize(rawQuery);   // Claude → a canonical query string
  if (!normalized) return deterministic;             // no key / timeout → deterministic fallback

  const upgraded = answerQuery(normalized);          // the ENGINE computes the real number
  return { ...upgraded, query: rawQuery };            // but show what the user actually typed
}
What it does

"Who saw red for the Yanks in the last 32" is meaningless to the parser. The model (cheap Haiku, temperature: 0, a JSON-schema-constrained intent) maps it to most red cards United States round of 32, which re-parses cleanly and runs against real event data. With no API key it's a no-op — the deterministic path is the graceful fallback, so the LLM is a strict upgrade, never a dependency.

src/lib/labMath.ts

06 · Exact Shapley values, from scratch, no libraries.

The idea. The Model Lab exists to show the math, not import a black box, so every kernel — PCA by power-iteration, k-means++, the reliability-diagram binning, and this Shapley attribution — is written from first principles and runs identically on the server and in the browser. Shapley explains a single prediction: how much each factor (home edge, both attacks, both defenses) contributed.

The code
// Exact Shapley: average each factor's marginal contribution over EVERY
// subset of the others. Order-independent; sums to v(all) − v(none).
export function shapleyContributions(factorKeys, v) {
  const m = factorKeys.length;
  const weight = (s) => (fact(s) * fact(m - s - 1)) / fact(m);   // |S|!·(m−|S|−1)!/m!
  for (const f of factorKeys) {
    let phi = 0;
    for (let mask = 0; mask < (1 << (m - 1)); mask++) {   // every subset S of the others
      phi += weight(S.size) * (v(withF) - v(S));           // marginal gain of adding f
    }
    out[f] = phi;
  }
  return out;
}
What it does

It enumerates all 2ⁿ coalitions of the other factors, weights each marginal gain by the exact Shapley coefficient, and sums — giving contributions that are order-independent and add up precisely to the model's output minus its neutral baseline. The waterfall chart in the Lab is a direct render of this map. It's tractable here because there are only ~6 factors; the code even says so.

src/data/loadTournament.ts

07 · Guarding against a feed that lies for one tick.

The idea. The live pipeline trusts a real, mid-tournament third-party feed — which occasionally glitches. On one refresh tick a fixture that's plainly in play can come back as "not started," and trusting that single reading flips the match out of every live surface until the next good tick ("the live match vanished"). The invariant: a started match can't un-start.

The code
// A started match can't un-start. Ignore a single spurious "not started"
// feed tick for a match already live / at half-time within its window. (WC-077)
export function isSpuriousRevert(matchStatus, feedStatus, withinWindow) {
  return withinWindow
    && feedStatus === 'SCHEDULED'
    && (matchStatus === 'LIVE' || matchStatus === 'HALFTIME');
}
What it does

In the refresh merge, a feed reading that trips this guard is dropped for that tick — the in-play state is kept — while a genuine full-time still finishes the match and a real drop past the play window still self-heals to finished. It's one predicate, but it's the difference between a stable live view and a match that flickers in and out. It also has a dedicated hermetic test, because that's how every one of these guards earns its place.

Above the store: IO, a lying feed, entropy. Below it: pure functions you can test offline. Every excerpt here lives on one side of that line — and that line is the whole architecture.

How the system is built

A live football-analytics engine with no database and a simulation for a heartbeat.

World Cup Intelligence tracks every match, player, and bracket of the 2026 World Cup live; runs an 8,000-simulation Monte Carlo forecast; answers natural-language questions; and degrades gracefully to a deterministic simulation when the live feed isn't there. This is how the ~24k lines fit together — and the handful of decisions that shape all of it.

A background loop re-polls the fixtures feed, merges live status/score/minute into the snapshot, and swaps in a new snapshot object so the engine and the store's indexes rebuild against fresh data. 03

The layers, top to bottom.

Six layers, each depending only on the one above it. The store is the seam: above it is IO and uncertainty; below it is deterministic computation.

Domain model

src/domain/types.ts

One file defines every shape in the system. Crucially, MatchStatus is a real lifecycle — SCHEDULED · LIVE · HALFTIME · FINISHED — and matches carry live phase, penalties, and per-team stats, so the rest of the code never has to guess what "in play" means.

Data source abstraction

src/data/providers · loadTournament · tournaments

A provider interface lets one DATA_SOURCE env select the feed: seed (offline simulation), statsbomb (real historical), or apifootball (live 2026). A registry holds every tournament — the live edition plus 27 historical World Cups (1930–2015) and deep StatsBomb editions — behind the same interface.

The live path is layered: fetch the API-Football snapshot, apply a frozen overlay (data captured from SportMonks before its trial lapsed, filling fields API-Football lacks), then enrich team metadata.

The store

src/data/store.ts

The active DatasetSnapshot lives on globalThis so it survives Next's dev/runtime module-instance split. Lookup indexes (by team, by match) are keyed to the snapshot's identity and rebuilt when a new snapshot swaps in — the fix for a whole class of "live data loaded but rendered empty" bugs where module-scoped caches went stale.

The analytics engine

src/analytics/

A pure function of the snapshot, memoized per snapshot identity so it computes once. It produces standings, ELO, a bivariate-Poisson win/draw/loss prediction per match, an 8,000-run Monte Carlo forecast (reach-probabilities, title odds, expected finish), power rankings, the golden-boot race, and momentum (comebacks, clutch goals, upsets).

The frontend

App Router server components (mostly force-dynamic) render the view models. A thin client island (LiveRefresh) polls /api/live-status and calls router.refresh() when the snapshot changes, so every page updates in place with no manual reload. 04

The live pipeline — the hardest part.

Everything upstream of the store deals with a real, mid-tournament, incomplete third-party feed. This is where most of the engineering lives.

Boot. instrumentation.register() fires once at server start and loads the live snapshot in the background, so the server accepts traffic immediately and serves the simulation until real data swaps in (with a loading indicator, never the placeholder shown as real).

Refresh loop. An adaptive timer re-polls just the fixtures feed — faster while a match is in play (~30s), slower when idle (~60s), and only when a match is actually in its play window, so it sips the API quota. It merges status, score, minute, and live phase into the current snapshot and swaps in a fresh snapshot object so the engine rebuilds only on a status flip.

The guards. A started match can't un-start, so a single spurious "not started" tick is ignored; a match stuck live past its window self-heals to finished; extra time and penalty shootouts are first-class. These are the accumulated lessons of watching real matches misbehave.

the resilience ladder

Three rungs, by design: live → a last-known-good snapshot stashed in Upstash Redis (survives Render's deploy-time disk wipe) → the deterministic simulation. A visitor banner names the current rung, and on a spent API quota the adapter fails fast into a 15-minute back-off instead of hammering a dead budget.

observability

/api/live-status?debug=1 is a quota-free readout of exactly what the server believes about every in-play match — status, minute, kickoff age, visibility, and the cache/back-off flags — so a "the live match vanished" report is diagnosable without touching the feed.

05

The AI layer: a translator, not an answerer.

The natural-language layer is deterministic first, with a language model used only to normalize questions it can't parse — so answers are always grounded in real numbers.

A question to /api/ask runs through smartAnswer: first the deterministic parser (src/ai/nlq.ts) resolves intent, scope (nationality, region, club), stage, and metric against the engine. Only if it returns unknown does llmParse.ts call Claude Haiku — not to answer, but to rewrite the free-form question into a canonical query string that re-runs through the same deterministic engine. The model never invents a statistic; with no API key, the deterministic path is the graceful fallback.

Search and NLQ share one entity resolver (src/ai/query/resolver.ts) — full name, surname, "F. Last", accents, typos, team codes and aliases — verified by a generative coverage corpus, so a name resolves identically everywhere. Alongside it, narratives.ts generates the daily briefing, match summaries, and insight cards, all recency- and phase-gated so nothing stale or fabricated surfaces.

The engine answers; the model only rephrases the question. That one boundary is why an AI feature can sit on top of accounting-grade numbers without hallucinating them.
06

The decisions that shape everything.

Most of the codebase's character comes from a small number of deliberate choices.

A No database

The whole tournament boots from a deterministic simulation (seeded PRNG) — npm run dev runs the full 48-team event with zero infrastructure or keys. The sim doubles as the resilience fallback and the test fixture.

B Snapshot-keyed state

State lives on globalThis and every memoized index is keyed to the snapshot's identity, so a snapshot swap can never leave a stale index pointing at old data — the root fix for the nastiest live-load bugs.

C Provider abstraction + overlay

One interface behind DATA_SOURCE; a mid-tournament SportMonks → API-Football migration was absorbed with a frozen overlay that backfills the fields the new provider lacks. Swapping feeds doesn't ripple through the app.

D Observed ≠ modeled

Predictions are cordoned from facts by a global toggle, and every status sentence is phase-aware (a knockout has no draw; a group table is history once the bracket starts) — so the app never shows a guess as a fact.

E LLM as translator

The model normalizes unknown questions into canonical queries; the deterministic engine produces every number. Grounded by construction, and a no-op without a key.

F Resilience by ladder

Live → Upstash last-known-good cache → simulation, with rate-limit back-off, a self-healing boot loop, and a visitor banner that never lets fallback data masquerade as live.

07

Testing & deployment.

The regression net grew one hermetic test per bug; the deploy is deliberately boring.

Tests. 112 Vitest tests across the analytics, AI, and data layers. They're hermetic — a test injects a synthetic match into a fresh snapshot, asserts, and restores it in a finally — so they run offline with no live API. Pure kernels (the Poisson grid, the state-machine guards, the calibration grading) are tested directly; server-only/client-only are stubbed so server modules load under Vitest.

Pipeline. Strict TypeScript with zero errors (npm run typecheck), a production build of 28 routes, and data-prep scripts (data:statsbomb, data:datahub, data:clubs) that precompute the historical editions offline. Deployed on Render; state is process-memory plus Upstash Redis (over REST — no client dependency) for the two things that must survive a redeploy: the prediction log and the last-known-good live snapshot.
